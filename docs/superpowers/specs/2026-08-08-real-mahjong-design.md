# Real Mahjong — 設計仕様書

作成日: 2026-08-08

Web ブラウザで動作する4人対戦オンライン麻雀。雀魂を参照点として、捨て牌・リーチ・ツモ・鳴き・和了の演出を作り込む。サーバ権威 + イベントソーシングを基盤とし、実装は複数の AI エージェント（Claude / Codex / opencode）が Orca の worktree オーケストレーションで並行して行う。

---

## 1. 前提と決定事項

ヒアリングで確定した要件。

| 項目 | 決定 |
|---|---|
| ゴール | 個人開発だが一般公開する完成品を目指す |
| 描画方針 | 3D卓・3D牌 + 2Dキャラ演出（雀魂と同じ構成） |
| 実装言語 | 麻雀エンジンは Rust、クライアントへは WASM で共有。サーバも Rust |
| ルール | 四人打ち、雀魂「金の間」準拠 |
| CPU雀士 | v1 から実装（ルールベース） |
| v1 運用機能 | 再接続復帰 / 牌譜の保存と再生 / アカウントと段位・レート / 友達対戦（部屋） |
| アセット | 市販・フリー素材中心、差し替え可能な構造にする |
| インフラ | 単一 VPS。卓はインメモリ保持。Postgres は永続化と牌譜のみ |
| 実装体制 | Claude / Codex / opencode によるマルチエージェント並行実装 |

### 1.1 スコープに関する明記

v1 の機能範囲は個人開発としては大きい。本仕様は範囲を削らず全体を設計するが、**届ける順序**を3段に切る（第10章）。設計を縮めるのではなく、実装の到達順を定義する。

## 2. アーキテクチャ方針

### 2.1 採用案：サーバ権威 + イベントソーシング

サーバが局の唯一の真実を持ち、進行を**イベント列**として生成する。各プレイヤーには視界フィルタをかけたイベントのみを配信する。クライアントは受信イベントを演出タイムラインとして消費する。

この方式を採る理由は、v1 に必要な4機能のうち3つが副産物として得られること。

- **牌譜** = イベント列そのもの
- **リプレイ** = 保存したイベントをクライアントへ流し直す
- **再接続** = スナップショット + 以降のイベント再送
- **演出** = イベントが演出の発火点そのもの

個人開発において「作る量が減る」ことを最優先の判断基準とした。

### 2.2 不採用案と理由

**状態同期型（毎回フルステートを送る）** — 実装は単純だがクライアントが差分から何が起きたかを逆算せねばならず、手出し／ツモ切りの区別のような演出に必須の情報が復元しづらい。牌譜も別建てになる。

**決定的シミュレーション（シード共有・ロックステップ）** — WASM でエンジンを共有しているため技術的には成立し帯域も最小だが、**クライアントが山を復元できてしまう**ため対人戦では採用不可。

ただしエンジンが決定的であること自体は捨てない。終局後にシードを開示すれば、クライアントは同じエンジンを回して牌譜と一致するかを検算できる。これが 5.5 のシードコミットメント検証である。対人戦の進行中は使わず、確定済みの過去の局に対してのみ用いる。

## 3. モジュール境界

### 3.1 構成

Cargo workspace + pnpm workspace の monorepo。

```
crates/
  protocol/        イベント / コマンド / 演出カタログ ← 最初に凍結する契約
  mahjong-core/    純粋判定。乱数もI/Oも時間も持たない
  mahjong-engine/  局・半荘の進行ステートマシン。シードを注入されイベントを吐く
  mahjong-ai/      ルールベースCPU。core にのみ依存
  mahjong-wasm/    core の判定系のみをクライアントへ公開
  server/          axum + tokio。WS・卓Actor・永続化・マッチング
apps/web/          Vite + TypeScript + Three.js
assets/            差し替え可能なマニフェスト管理
```

### 3.2 境界を引く原則

**純粋な部分をできるだけ大きく、I/O と時間を持つ部分をできるだけ小さく。**

麻雀は点数計算の誤りが致命傷になるため、テスト可能性を構造で担保する。

**mahjong-core** — 牌の表現、向聴数、待ち、和了判定、役判定、符計算、点数計算、鳴きの可否、振聴判定。すべて純粋関数。乱数が一切入らないため、既知の牌譜を流し込む回帰テストが成立する。

**mahjong-engine** — 配牌からツモ、打牌、反応ウィンドウ、流局、連荘までの進行。山の生成はシードを外部から注入する。時間も外部から与える。エンジン自体は決定的であり、同じシードと同じ入力からは必ず同じイベント列が出る。これがリプレイ検証と不具合再現を可能にする。

**server** — 唯一 I/O と時間を持つ層。1卓 = 1 tokio task の Actor とし、卓同士を完全に独立させる。

**mahjong-wasm** — クライアントには `core` の**判定系のみ**を公開する。向聴数計算や「いま何が鳴けるか」の表示に使う。山を持つ `engine` は決してクライアントへ出さない。

### 3.3 マルチエージェント実装のための追加制約

**クレート = 作業単位 = worktree。** Cargo workspace により、あるエージェントは他クレートが未完成のまま `cargo test -p mahjong-core` を回せる。これが並行実装の前提条件。

**契約を先に凍結する。** `protocol` クレート（イベント型・コマンド型・演出カタログ）は並行作業の**前**に単独で書き切る。ここが動くと全エージェントの手戻りになるため、Wave 0 として分離する。

**モジュール木を先に宣言する。** Rust では `lib.rs` の `mod` 宣言が全エージェントの触る共有ファイルとなり、マージのたびに衝突する。足場コミットで空ファイルとモジュール宣言まで先に配置し、各エージェントは**自分のファイルの中身のみ**を書く。

**テストを仕様書にする。** 「七対子は25符固定」「食い下がりの扱い」のような解釈の揺れは、エージェントごとに異なる実装を生む。**期待値テーブル（役判定ケース・点数計算ケース）を本仕様および足場コミットに含め**、各エージェントには「このテストを通せ」と渡す。各作業単位の完了条件が機械判定可能になる。

## 5. イベントモデルとデータフロー

### 5.1 データフロー

```
Client ──Command──▶ 卓Actor ──▶ engine.apply(cmd) ──▶ Vec<Event>（真実）
                                                        │
                                        ┌───────────────┼──────────────┐
                                        ▼               ▼              ▼
                                   牌譜へ追記      project(seat)    タイマー更新
                                   (append-only)   ×4 → WS配信
```

牌譜への追記はインメモリの append-only バッファに対して行い、**DB への書き出しは局の境界でまとめて行う**（理由は 8.3）。

### 5.2 Command

クライアントが送れるものは以下に限る。

```
Discard { tile, riichi: bool }
CallResponse { Pon | Chi | Kan | Ron | Pass }
Ankan { tile }
Kakan { tile }
Tsumo
Kyuushu
```

サーバは受け取ったコマンドを**エンジンが計算した合法手集合と必ず照合**し、外れていれば拒否して現在の合法手を再送する。「クライアントを信用しない」という原則をこの一点に集約する。

### 5.3 Event 設計の要点

演出に必要な情報は、逆算ではなくイベント自身に持たせる。

```rust
Discard { seat, tile, manner: Tedashi | Tsumogiri }
```

手出しかツモ切りかを明示的に持つ。状態同期型ではクライアントが差分から逆算するしかなかった情報だが、これは演出（牌の出現位置と軌道が変わる）と戦術情報（河の手出し表示）の双方に必須である。

主要イベント：

```
RoundStart { round, dealer, honba, riichi_sticks, seed_commit }
Deal { hands, dora_indicator }
Draw { seat, tile, source: Wall | DeadWall }
Discard { seat, tile, manner }
Riichi { seat, step: Declare | Accepted }
Call { seat, kind, from, tiles }
KanDeclared { seat, kind, tile }          -- 加槓の槍槓受付を可能にする
DoraReveal { indicator }
ActionPassed { seat, window_id, declined } -- 見逃しの記録
Agari { results, settlement }
Ryuukyoku { kind, initiator, tenpai, revealed_hands, nagashi_winners, settlement }
RoundEnd { scores, next, reason }
RequestAction { seat, window_id, options, deadline_ms }
```

すべてのイベントに連番 `seq` を振る（第8章の再接続で使用）。

### 5.3.1 進行と精算のために追加で持つ情報

素朴なイベント定義では表現できない局面がある。以下は型として持たせる。

**反応ウィンドウ ID。** `RequestAction` と `CallResponse` の双方が `window_id` を持つ。これがないと、遅延した応答や再送が「どの打牌に対する応答か」を判別できず、間違ったウィンドウに適用されうる。

**加槓の段階分離。** 加槓は「宣言 → 槍槓の反応ウィンドウ → 成立 → 嶺上ツモ」という順序を踏む。完成済みの `Call { kind: Kakan }` だけでは槍槓を受け付ける余地がない。`KanDeclared` を分けて発行する。

**見逃しの記録。** ロン可能な局面でのパスは同巡内フリテンを発生させ、リーチ後なら以後の和了を制約する。コマンドは牌譜に残らないため、`ActionPassed` をサーバ側イベントとして残す。

**責任払い（パオ）。** 大三元・大四喜の確定牌を鳴かせた者は、ツモ和了なら全額、ロン和了なら放銃者と折半する。和了結果に責任者・対象役・負担形式を持たせる。

**流し満貫。** 荒牌流局の一種だが、テンパイ料とは別の精算になる。`Ryuukyoku` に成立者を持たせる。

**精算内訳。** `score_delta` の最終差分だけでは、ダブロン時にリーチ供託を誰が取ったか、本場をどちらに付けたかを牌譜から復元できない。和了者ごとに素点・本場・供託・責任払いを分けて記録する。

**連荘の理由。** 親和了・親テンパイ流局・途中流局・流し満貫で、局と本場の進み方が変わる。`RoundEnd` に判断理由を持たせ、エンジンの判断を牌譜から監査できるようにする。

**九種九牌の宣言者と槓の分布。** `Ryuukyoku` に `initiator` を持たせる。四開槓の判定には席ごとの確定槓数が要るため、局状態で保持する。

### 5.4 視界フィルタ

不正対策の全体重をここが支える。

```rust
fn project(ev: &Event, viewer: Seat) -> Option<ClientEvent>
```

- `Draw` — 自分は牌つき。他家は牌なし（ただし手出し／ツモ切りと手牌枚数は見える）
- `Deal` — 自分の13枚のみ
- 裏ドラ — `Agari` イベントに初めて同梱される。それまでクライアントに存在しない
- 山 — 残り枚数のみ

**この関数を1箇所に集約する。**「サーバから出ていくバイト列に見えてはならない情報が含まれない」というテストをここへ集中させる（第9章）。

**型だけで防げない箇所には、射影側で判断を持たせる。**`ClientEvent` を `Event` と別型にすることで、隠すべき情報を運ぶ「場所」の多くは消える。ただし次の2つは、フィールドが存在すること自体は正当なので、型では守れない。

- `Ryuukyoku.revealed_hands` — 流局時に手牌を公開するのはテンパイ者だけである。生成側が全員の手牌を入れてしまえば、そのまま全席へ流れる。**射影側で流局種別と公開資格から公開席を決め直す**
- `Agari.ura_indicators` — 裏ドラはリーチ和了があったときにしか存在しない。空配列の運用規約に頼らず `Option` とし、リーチ成立済みの和了者がいない限り `None` であることを不変条件で検査する

この2つには、非公開であるべき手牌を混ぜた**負例テスト**を置く。「型として漏洩できない」と言えるのは前者の多くの箇所についてであり、ここは明示的な検査で守る。

### 5.5 シードのコミットメント

局開始時に山のシードの**ハッシュのみ**を `RoundStart.seed_commit` として配布し、**半荘の終了後に**全局分のシード本体をまとめて開示する。プレイヤーは牌譜とシードから、サーバが途中で山を操作していないことを自力で検算できる。

**開示を局終了時ではなく対局終了時にする**のが重要である。シードがあれば山全体を再構築でき、その局で公開されなかった他家の手牌まで復元できてしまう。局ごとに開示すると、以降の局で対戦相手の手の内を遡って知れることになり、同じ半荘の中で不公平が生じる。対局が終わってから開示すれば、検算の目的は変わらず果たせて、この抜け道が閉じる。

実装コストはハッシュ1個の配布と検証コマンドのみ。オンライン麻雀に必ず伴う「配牌操作の疑い」に技術的に回答できる。

## 6. 演出の時間モデル

雀魂級の演出とネットワーク対戦を両立させる中核。原則は**サーバは演出時間を知っているが、待たない**。

### 6.1 演出カタログ

`protocol` クレートに定数として置き、**サーバとクライアントが同じ値を見る**。

| イベント | 演出時間 |
|---|---|
| Draw | 250ms |
| Discard | 350ms |
| Pon / Chi | 700ms |
| Kan | 1100ms |
| RiichiDeclare | 1800ms（牌を倒す + リーチ棒 + カットイン） |
| DoraReveal | 800ms |

### 6.2 締切の計算

```
deadline = now + 基準思考時間 + 溜め時間バンク + lead_in + 通信猶予
                                                  ↑
                             直前イベント群の演出時間合計（カタログから算出）
```

**この設計が効く場面：** 下家がリーチを宣言した直後に自分の番が来る。リーチ演出は1800ms。サーバが素の思考時間だけで締切を切っていれば、プレイヤーは演出を見ている間に持ち時間を1.8秒失う。カタログをサーバも持つことで、演出分だけ締切が自動的に後退する。**演出が思考時間を食わない。**

通信猶予は 500ms とする。

### 6.3 クライアントの状態2層

```
受信 ClientEvent
      ├──▶ GameState       全イベント適用済み。常に最新。論理的な真実
      └──▶ PresentedState  演出タイムラインが消費した分まで。画面が描くのはこちら
```

演出は論理状態から遅れて追いつく。この分離がなければ再接続とタブ復帰で破綻する。

**追いつき方（catch-up policy）：** キューが閾値を超えたら再生速度を上げる。さらに超えたら演出を飛ばして状態のみ適用する。リロード復帰では演出を全スキップして最新盤面へジャンプする。

**演出スキップ**は再生速度を上げるのみで、締切は動かさない。上級者は速く打てるが、有利にも不利にもならない。

### 6.4 反応ウィンドウ（鳴き）

打牌のたびに鳴ける者へウィンドウを開く。優先度は **ロン > ポン / 明カン > チー**。

全員の応答を待つと、打牌のたびに数秒停止するゲームになる。**早期確定**を入れる。

> いま確定している最高優先の応答**以上**を出せる未応答者が存在しなければ、その時点で決定する。

「より上」ではなく「以上」であることが要点である。ダブロンを認める以上、ロンが1つ確定しても、**ロン可能な未応答者が残っている限り待たねばならない**。ここを「より上」にすると1人目のロンで確定してしまい、ダブロンと三家和流局が原理的に成立しなくなる。

- A はチーのみ可、B はポン可。**B がポンと答えた瞬間、A を待たずにポン確定**（ポン > チー、かつ同順位の未応答者なし）
- A がチーと答えたが B が未応答 → B を待つ（B がポンならそちらが優先）
- A がロンと答えたが B もロン可能で未応答 → **B を待つ**（ダブロンの判定に必要）
- 鳴ける者がゼロなら、ウィンドウを開かずに次のツモへ進む（実際にはこれが大半）
- タイムアウトはパスとして扱う

**同順位で複数人が名乗り出られるのはロンだけである。**牌は1種4枚しかないため、2人が同じ牌をポンするには各自2枚＋捨て牌1枚で計5枚必要になり成立しない。ポン（2枚）と明槓（3枚）の競合も6枚必要で不可能。チーは上家しかできないためチー同士も起きない。したがって非ロンの同順位競合を解決する席順ロジックは実装せず、**発生しないことをエンジンの不変条件として検査する**。

**情報漏洩への対処：** 鳴ける者がいない局面のみ即座に進むと、間が空いたこと自体が「誰かが鳴きを検討している」という情報になる。これを防ぐため、**打牌から次のツモまでには、鳴ける者の有無にかかわらず必ず一律 350ms の待機を挟む**。

したがって挙動は次の2通りに整理される。

- 鳴ける者がゼロ → ウィンドウは開かないが、350ms 待ってから次のツモへ
- 鳴ける者がいる → ウィンドウを開く。早期確定またはタイムアウトで決着するが、決着が 350ms より早くても 350ms までは次へ進まない

この 350ms は打牌演出（6.1）と同じ長さである。値を揃えることで「次の行動が、直前の演出の完了より論理的に先行する」状態が起きなくなる。なおクライアントは受信キューを順に再生し PresentedState は論理状態から遅れるため（6.3）、仮に待機が演出より短くても表示が割り込まれることはない。値を揃えるのは実装者が毎回この推論を辿らずに済むようにするためである。

「ウィンドウを開くか」と「次へ進むまでの最短時間」を別の概念として扱う点が要点である。

この早期確定ロジックは `engine` 側の純粋関数として実装し、テストで固定する。

## 7. クライアント描画と演出

### 7.1 牌のレンダリング

136枚すべてを個別メッシュにするとドローコールが増えるが、実際に**動く牌はごく一部**である。山は側面しか見えず、ツモる1枚以外は動かない。

**山はバッチした1メッシュ、動く牌のみ個別メッシュ**とする。ツモる瞬間に山から1枚を個別メッシュとして切り出し、河に着地したら河のバッチへ焼き込む。同時に個別で存在するのは手牌・鳴き・河の直近数枚のみで、常時50前後に収まる。モバイルでも余裕がある。

牌面は34種 + 裏 + 赤ドラ3種を**アトラス1枚**にまとめ、UV オフセットで切り替える。形状は角丸ボックス、牌面（白）と牌体（黄）を1マテリアルで持つ。

**動的シャドウは使わない。** 卓は固定なので環境マップとベイクした AO で焼き、牌の影は接地影（ソフトな楕円デカール）とする。リアルタイムシャドウマップより高速で、見た目はほぼ変わらない。カメラは自席からの固定俯瞰。和了時のみカメラワークを入れる。

### 7.2 2D と 3D の境界

判断基準を一つに定める — **画面座標に置く演出は2D、卓座標に置く演出は3D**。

- **3D側** — 牌が光る、リーチ棒が卓中央へ飛ぶ、ドラ表示牌がめくれる、和了時に手牌が開く
- **2D側** — リーチカットイン、役表示パネル、点数移動、キャラ立ち絵、和了時の役リスト

2D は Three.js キャンバス上に重ねた DOM オーバーレイで実装する。テキストのレイアウトとアニメーションは DOM/CSS の方が容易であり、ベクタなので文字が鮮明である。3D 空間へテキストを焼くことは行わない。

### 7.3 演出プラグイン

```ts
interface EffectPlugin {
  id: string
  match(ev: ClientEvent, ctx: EffectContext): boolean
  play(ev: ClientEvent, ctx: EffectContext): Timeline
}
```

**`Timeline` は宣言的とする。** `async/await` で記述するとスキップ・早送り・catch-up が実装不能になる。**時刻 `t` を与えれば状態が決まる `seek(t)` 可能な形**とする。6.3 のスキップと追いつきはこの一点によって成立する。

キャラ演出は**別バンドルのプラグイン集合**として後から `register` する。キャラを一切ロードしなくとも基本プラグインのみでゲームは完全に成立する。素材の完成を待たずに開発が進み、キャラを切った軽量モードも自然に得られる。

### 7.4 アセットマニフェスト

市販・フリー素材中心のため差し替えを前提とする。牌テクスチャ・卓・SE・ボイス・立ち絵を JSON マニフェストで参照し、**ライセンス情報も併せて保持してクレジット画面を自動生成する**。素材を寄せ集める以上、これは必ず必要になるため最初から入れる。

音は WebAudio で、演出タイムラインと同一クロックで駆動する。ブラウザの自動再生制限があるため、最初のユーザー操作で AudioContext を resume する。

## 8. エラー処理と再接続

**卓は接続状態と無関係に進行する。** 誰かが落ちても対局は停止しない。

### 8.1 再接続

クライアントは最後に受信した `seq` を保持し、復帰時に `Resume { table_id, token, last_seq }` を送る。サーバの応答は差分の大きさで分岐する。

- 差分が小さい → そこからのイベントのみ送信
- 差分が大きい / 初回 → 視界フィルタ済みスナップショット + 以降のイベント

演出は差分が小さければ再生し、大きければスキップして最新盤面へジャンプする（6.3 の catch-up と同一機構）。

### 8.2 切断中の扱い

締切でツモ切りとする。ただし和了可能な状態であれば自動で和了る。**連続して自動打牌が続いた場合は CPU 代打ちへ切り替える**。他の3人を待たせ続けないため、v1 で CPU を実装する価値がここでも生きる。

### 8.3 サーバの失敗

卓 Actor を tokio task 境界で隔離し、ある卓の panic が他卓へ波及しないようにする。

永続化は**局の境界**で行う。プロセスが落ちた場合、進行中の局は破棄して局頭から再開する（点数と本場は保たれる）。毎イベントの DB 書き込みは単一 VPS では割に合わないため、これは意図的な妥協である。失われるのは最大1局分の進行のみで、点棒は失われない。

### 8.4 不正コマンド

合法手集合と照合して拒否し、現在の合法手を再送してログに残す。対策であると同時に、**自クライアントのバグ発見器**として機能する。

### 8.5 エンジンの不変条件

毎イベントで検査する。

- 牌の総数が常に136枚（山 + 手牌 + 河 + 鳴き + 王牌）
- 点棒の合計が常に一定（供託込み）

`debug_assert` で仕込み、プロパティテストで大量に踏ませる。

## 9. テスト戦略

`core` と `engine` が I/O も時間も持たないため、対局を高速に回せる。これが戦略全体の土台である。

### 9.1 実測値と、そこから見直した前提

Wave 1a 完了時点の実測（Apple Silicon / release ビルド）:

| 処理 | 1回あたり |
|---|---|
| `shanten`（3形の統合） | 3.7 µs |
| `waiting_tiles`（34種を試行） | 5.3 µs |

**当初「毎秒数千局」と見込んでいたが、これは楽観的すぎた。** 仮に CPU が毎巡14通りの打牌候補を向聴計算で評価するとすれば1局あたり約4000回の呼び出しとなり、**毎秒60〜70局**にとどまる。

ただしこの数字は AI の設計（Wave 3）に強く依存する。エンジン自身が必要とする向聴計算はツモごとのテンパイ判定程度で、1局あたり数百回に収まる。したがって現時点で最適化するのは早い。

**判断を保留し、Wave 3 で AI を実装した時点で再測定する。**そのとき不足していれば、向聴計算に次のいずれかを入れる。

- 探索結果のメモ化（同一手の再計算を避ける）
- 色ごとの部分パターンを事前計算したテーブル引き（一般に1桁以上速い）

下表のプロパティテストが「1万局」を回す前提も、この実測に照らすと数分かかる。CI では回数を絞り、定期実行で全量を回す形にする。

| 層 | 方法 |
|---|---|
| `core` | 期待値テーブル駆動（役・符・点数）。公開牌譜を流す回帰テスト |
| `engine` | proptest でランダムシード1万局。全イベントで不変条件を検証 |
| 視界フィルタ | **配信イベント列から他家の手牌と山が復元できないこと**を検証 |
| `server` | CPU4人の通し対局を卓 Actor 経由で最後まで実行 |
| 演出 | `Timeline` は `seek(t)` 可能な純粋関数のため、時刻を与えて状態検証 |
| 結合 | 実サーバ + ヘッドレス4クライアントで通し対局 |

**この表がそのままマルチエージェント実装の完了条件となる。** 各エージェントには「このテストを通せ」と渡し、結合時にコーディネータが検証する。

## 10. 実装計画

### 10.1 到達段階

機能を削るのではなく、届ける順序を定義する。

| 段階 | 到達点 |
|---|---|
| 第1段 | 対局が成立する最小核。CPU4人 + 人間1人が最後まで打てる。演出は最低限 |
| 第2段 | 運用機能。アカウント・段位・再接続・牌譜・部屋・マッチング |
| 第3段 | フル演出。キャラ立ち絵・カットイン・ボイス・和了カメラワーク |

### 10.2 実装の波（Wave）

依存関係から並行可能な単位を切る。

| Wave | 内容 | 並行度 |
|---|---|---|
| 0 | 足場 + `protocol` 凍結 + 共有語彙 + 期待値テーブル整備 | 単独（コーディネータ） |
| 1 | core判定系 / core点数系 / 3D卓・牌の描画 / 演出タイムライン骨格 | 4並列 |
| 2 | engine進行 / WASM橋渡し / server骨格・卓Actor | 3並列 |
| 3 | CPU雀士 / 演出プラグイン群 / 永続化・牌譜 / マッチング・部屋 | 4並列 |
| 4 | 結合・通し対局・視界フィルタ検証 | 単独（コーディネータ） |

### 10.2.1 共有語彙を Wave 0 へ引き上げる

判定系（1a）と点数系（1b）は、素朴に分けると同じファイルを取り合う。符計算は待ち形（辺張・嵌張・単騎）を必要とし、ロンの可否は「最低1役」の確認を必要とし、向聴計算と役判定はどちらも面子分解を必要とする。

解決は**契約を先に凍結する**という Wave 0 の原則をそのまま延長することである。両者が共有する**語彙（型）を Wave 0 で定義し、それを使う アルゴリズム を Wave 1 で分担する**。

Wave 0 へ引き上げるもの：

- **手牌の集計表現**（`[u8; 34]` と操作） — 双方が同じ表現の上で書く
- **待ち形** `WaitShape { Ryanmen, Penchan, Kanchan, Shanpon, Tanki }` — 1a が算出し、1b が符計算で消費する
- **和了形の分解結果** `Decomposition` — 1b が生成し、必要なら 1a も参照できる

型が先にあるため、1b は 1a の実装完了を待たずに `WaitShape` を直接組み立ててテストを書ける。両者が同時に着手できる。

### 10.2.2 ファイル所有権

Wave 1 の各エージェントが編集してよいファイルを事前に確定する。所有者のいないファイルを作らない。

| ファイル | 所有 | 備考 |
|---|---|---|
| `hand.rs` | Wave 0 | 共有表現。Wave 1 では編集しない |
| `shanten/*.rs` | 1a | |
| `wait.rs` | 1a | 型は Wave 0、算出は 1a |
| `furiten.rs` | 1a | |
| `callable.rs` | 1a | チー・ポン・槓の候補のみ |
| `decompose.rs` | 1b | 1a は自前の探索を `shanten/standard.rs` 内に持ち、ここを編集しない |
| `yaku_check/*.rs` | 1b | |
| `fu.rs` | 1b | 待ち形は `wait.rs` の結果を消費し、判定を再実装しない |
| `score.rs` | 1b | |

**ロンの可否は 1a にも 1b にも置かない。**役の有無に依存するため、`callable.rs`（1a）の鳴き候補と `yaku_check`（1b）の役判定が揃った Wave 2 で、engine 側が結線する。単一ファイルを両者に編集させないための措置である。

### 10.3 エージェント割り当て

| エージェント | 担当領域 |
|---|---|
| **Codex** | 点数計算・向聴数・和了判定など、正解が一意でテストで白黒がつく密なアルゴリズム |
| **Claude**（コーディネータとは別 worktree のワーカー） | サーバの Actor 設計、演出タイムライン、設計判断が絡む部分 |
| **opencode** | 足場・CI・アセットマニフェスト・定型実装 |

### 10.4 オーケストレーション方式

Orca の worktree オーケストレーションを用いる。

- 作業単位ごとに `orca worktree create --agent <id> --prompt "<作業指示>"` で独立した checkout を切る
- opencode は既知エージェント ID ではないため、`orca terminal create --worktree <selector> --command "opencode"` で起動する
- 監督付き協調（タスク DAG・inbox/reply・完了確認）は `orca orchestration` 系コマンドで行う。単純な投げ切りではないため full handoff は用いない
- 各エージェントは worktree コメント（`orca worktree set --comment`）で進捗を報告する
- コーディネータは第9章のテストで各成果物を検証してから統合する
