# 見た目の完成度を上げる 設計

## 1. 何が問題か

**この作業期間に出た品質の指摘9件は、すべて利用者が見つけた。**開発側は1件も
先に見つけていない。試験は209件通り、型検査もビルドも通っている。

| 指摘 | 実際の原因 |
|---|---|
| 牌が文字ラベル | 牌面を持っていなかった |
| 牌がほぼ全部別の牌に化ける | アトラスの行が上下反転 |
| 牌面が焼けない | SVG に `xmlns` が無い |
| 取ってつけたような3D | 面取りの無い直方体、厚みが実物の 0.75 倍 |
| 白に違和感 | 細い長方形1本で、枠に見えない |
| ボタンが押せない | 毎フレーム DOM を作り直していた |
| 手牌が読めない | 俯瞰カメラに対して牌を立てていた |
| 解像度が低い | 牌面1枚が 128px、異方性フィルタ無効 |
| 捨て牌が分からない | 直前の捨て牌を画面に出していなかった |

**共通点は「機械が見ていない層で起きている」ことである。**論理は試験で守られて
いるが、絵は誰も見ていない。人が気付くまで壊れたままになる。

したがって直すべきは個々の見た目ではなく、**見た目を扱う仕組み**である。

## 2. 何をするか

品質を4つの層に分け、**下の2層（素材・造形）を先に固める。**

| 層 | 中身 | 今回 |
|---|---|---|
| 素材 | 牌面・卓の絵 | **やる** |
| 造形 | 牌の形・質感・光 | **やる** |
| 手応え | 音・光・震え | 次回 |
| 情報 | 何が起きたか・何を選べるか | 次回 |

土台が汚いまま手応えを足しても効かない。順序を守る。

## 3. 素材

### 出所と許諾

Wikimedia Commons の牌図一式を使う。

- カテゴリ: `Category:SVG Planar illustrations of Mahjong tiles`（176件）
- 作者: Shizhao
- 許諾: **パブリックドメイン。**「いかなる条件も付けず、あらゆる目的での使用を
  認める」と明記されている（併せて GPLv2+ でも提供）
- 寸法: 75 x 95 px の SVG。ベクタなので拡大しても劣化しない

取り込むファイルは 34 種。

| 種類 | ファイル |
|---|---|
| 萬子 | `U+1F007_MJ1wan.svg` 〜 `U+1F00F_MJ9wan.svg` |
| 索子 | `U+1F010_MJ1tiao.svg` 〜 `U+1F018_MJ9tiao.svg` |
| 筒子 | `U+1F019_MJ1bing.svg` 〜 `U+1F021_MJ9bing.svg` |
| 風牌 | `0401東風.svg` `0403南風.svg` `0402西風.svg` `0404北風.svg` |
| 三元牌 | `0405中.svg` `0406發.svg` `0407白.svg` |

赤ドラ3種（五萬・五筒・五索）は、元の SVG の色を赤へ置換して作る。**別途
取り込まない。**ベクタなので置換で足りる。

`apps/web/src/assets/tiles/` へ置き、`apps/web/src/assets/tiles/CREDITS.md` に
出所・作者・許諾・取得日を記録する。パブリックドメインなので表示義務は無いが、
**記録が無いと後から出所を確かめられない。**

### 取り込み方

**実行時に SVG を読む今の仕組みをそのまま使う。**`face-atlas.ts` は既に SVG の
データ URL を画像として読み、アトラスへ焼いている。生成した SVG 文字列の代わりに、
取り込んだファイルの中身を渡すだけでよい。

ファイルは Vite の `?raw` で束ねる。**取得のための通信を増やさない。**37回の
読み込みは起動を目に見えて遅くする。

`ui/tile-face.ts` の自前描画は**残す。**2D の盤面（鳴きのボタン、和了の役表示）が
使っており、また素材が読めなかったときの控えになる。

## 4. 造形と質感

### 彫りの表現

実物の牌面は彫って色を入れたもので、平らな印刷ではない。**法線マップは作らない。**
生成の工程が増えるうえ、効果に対して費用が高い。代わりに、**アトラスへ焼く時点で
図の縁へ細い暗い線と明るい線を入れる**（内側に落ちる影と、反対側の照り返し）。
2D の処理で済み、どの光源でも彫りに見える。

### 象牙の質感

いまは一様な粗さ（0.42）である。牌面と側面で粗さを変える。面は磨かれて
わずかに艶があり、側面と背はそれより粗い。

### 光

いまは環境光と平行光の2灯だけで、牌の縁が光を拾わない。**半球光**を足し、
上からの明かりと卓面からの照り返しを分ける。牌の角の面取りが光を拾い、
輪郭が出る。

### 接地

影が無いため牌が浮いて見える。仕様は動的シャドウを禁じている
（`docs/superpowers/specs/2026-08-08-real-mahjong-design.md:363`）ので、
**牌の下に柔らかい黒の板を1枚敷く。**共有のぼかしテクスチャを貼った四角形で、
卓面に寝かせて置く。手牌・河・副露にだけ付ける（山には付けない。136枚ぶんは
描画量に見合わない）。

**この項目は最も削りやすい。**効果が薄いと判断したら落とす。

## 5. 見本比較の仕組み

### 何を撮るか

2種類を撮る。

1. **牌姿一覧** — 37種（34＋赤ドラ3）と裏面を並べた1枚。牌が化けたら必ず出る
2. **盤面** — 配牌直後・副露5種・リーチ・長い河・和了。`preview.html` の
   決め打ち盤面を使う（対局に依存させない）

### どう判定するか

承認済みの見本と画素で比べ、**差が閾値を超えたら落とす。**閾値は「1画素でも
違えば落とす」にはしない。描画には環境差があり、それでは毎回落ちて誰も見なく
なる。**異なる画素の割合**で見る。

**見本の更新は人間が承認する。**新しい見本が良いか悪いかは機械には決められない。
差分が出たら `【要確認】` で上げ、承認されたときだけ見本を差し替える。

### 前提となる危険

**この仕組みは、ヘッドレスの描画が安定して動くことに依存する。**現在それが
壊れている。作業期間の後半、ヘッドレス Chrome が画像を書き出さなくなり、
牌を作り直した結果を一度も目で確認できていない。

したがって**最初の作業は撮影経路を直すことである。**ここが直らなければ、
以降の項目はどれも検証できない。直せない場合は、この設計を見直す。

## 6. やらないこと

- 音、キャラ立ち絵、カットイン、和了のカメラワーク
- 卓の木目や布地の作り込み（牌が先）
- 山のバッチ化などの描画性能の作業（別途）

**土台が汚いまま手応えを足しても効かない。**

## 7. 受け入れの基準

- 37種すべてが、実物の牌図として判別できる
- 牌が板ではなく立体に見える（面取りが光を拾い、接地の影がある）
- 牌姿一覧と主要な盤面が見本として承認され、以後の崩れを機械が検出する
- 既存の 209 件の試験が通り続ける

**「綺麗になったか」は人間が決める。**機械が決めるのは「承認された状態から
崩れていないか」だけである。
